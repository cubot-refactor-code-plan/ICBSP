# ICBSP 编码风格规范

> 本文档以 `code/bsp/bsp_uart.{hpp,cpp}` 为基准样板整理而成，是工程库统一遵循的标准。
> 格式类规则已固化在 `.clang-format` 中（保存时自动格式化），命名、注释、架构类规则需人工遵守。

---

## 1. 文件组织

| 规则 | 说明 |
|---|---|
| 文件名 | 全小写 + 下划线：`bsp_uart.hpp`、`dji_motor.hpp`、`pid.hpp` |
| C++ 头后缀 | `.hpp` |
| C++ 源后缀 | `.cpp` |
| C 调用 C++ 的转接头 | 纯 C 头，内含 `extern "C"`：宿主的 `app_main.h`（`app_init()`），库的 `service/system/system.hpp` |
| 正常 C++ 头 | 层由所在目录决定，文件名不强制带层前缀：BSP 沿用 `bsp_xxx`，设备用 `device_xxx` 或设备名（`dji_motor`），算法直接用名字（`pid`） |
| 头文件保护 | `#ifndef __XXX_HPP__` + `#define` + 末尾 `#endif // __XXX_HPP__` |
| 包含路径 | 库只把 `code/` 加进包含路径，库头文件一律写全子目录（`#include "service/system/status.hpp"`），宿主文件（`hardware_config.h`、`board_instances.hpp`）写文件名；下层文件里不出现上层目录（层次：`algorithm`、`bsp` → `service` → `device` → `tasks`；例外是纯状态码 `service/system/status_code.hpp` 与配置入口 `service/system/config_check.hpp`，各层都能包含）。`python3 tools/check_layers.py` 检查 |
| 库的 HAL 依赖 | 库内只包含 `bsp/bsp_series.hpp`（由它按系列包含 `stm32h7xx_hal.h` / `stm32f4xx_hal.h`），不包含 CubeMX 按外设生成的 `main.h` / `fdcan.h` / `usart.h` / `tim.h`；依赖某个外设的模块整体包在 `#ifdef HAL_xxx_MODULE_ENABLED` 里（头文件在保护宏内、源文件整文件） |
| 文件说明块 | 只写在头文件最顶部；源文件最顶部不放任何说明，直接以 `#include` 开头。没有对应头文件的源文件（`service/system/newlib_lock.cpp`，只提供弱符号）例外，说明块写在它自己顶部 |

间接使用的头文件在行尾加 `// IWYU pragma: keep`，规避 clangd 误报。

## 2. 命名规范（库与宿主应用）

| 元素 | 规则 | 示例 |
|---|---|---|
| 类名 | 大驼峰（模板类可加 `T` 后缀） | `BspUartT`、`DjiMotor`、`DeviceBmi088`、`EventState` |
| 结构体 | 大驼峰，不加 `_t` 后缀 | `ImuData`、`CanRxMsg`、`PID::Config` |
| 方法 / 自由函数 | 小写蛇形 | `init()`、`send()`、`calc()`、`system_init()` |
| 私有成员变量 | `_` 前缀 + 小写蛇形 | `_huart`、`_rx_stream_buffer`、`_diff_mode` |
| 枚举类型 | `enum class` + 大驼峰 | `UartDir`、`DjiMotorType`、`DiffMode` |
| 枚举值 | 全大写蛇形（型号名照写） | `NOT_INIT`、`DIFF_TARGET`、`M3508`、`J4340P` |
| 宏 / 常量 | 全大写蛇形；宏带 `ICBSP_` 前缀 | `ICBSP_CAN_CMD_EXPIRE_MS`、`TX_CAPACITY` |
| 模板参数 | 全大写蛇形 | `RX_SIZE`、`TX_DEPTH` |
| 全局实例 | 全小写蛇形 | `bsp_can1`、`bsp_uart1`、`imu_bmi088` |
| 类型别名 | 大驼峰（C 兼容 typedef） | `SysTaskStats`、`SystemReportHook` |

例外：
  1. 构造函数 / 析构函数必须与类名（大驼峰）一致，如 `DeviceBmi088::DeviceBmi088()`
  2. 外部库（HAL / FreeRTOS 等 C 库）强制要求固定名称的回调，如 `HAL_FDCAN_RxFifo0Callback`、`vApplicationStackOverflowHook`、`__io_putchar`、`_write`
  3. CubeMX 生成的默认任务名（如 `StartDefaultTask`）保留原名，以便 CubeMX 重新生成时同名兼容

### 2.1 查询、布尔与动作接口（Q10，阶段 2.7 起）

| 接口种类 | 规则 | 示例 |
|---|---|---|
| 查询（返回内部状态 / 数据，不改对象） | `get_` 前缀 | `get_data()`、`get_diag()`、`get_port()`、`get_position()`、`get_error_code()` |
| 布尔查询 | `is_` / `has_` 前缀，返回 `bool` | `is_online()`、`is_running()`、`is_initialized()`、`is_pressed()`、`is_failsafe()` |
| 动作 | 动词开头 | `init()`、`send()`、`update()`、`reset()`、`set_duty()`、`fill_data()`、`unpack()` |
| 读硬件 | `read_` 前缀（会访问外设寄存器，可能有副作用） | `read_delta()`、`read_raw()`、`read_reg()` |
| 取走（读完就清 / 消费掉的数据） | `take_` 前缀 | Emm_V5 的位置 / 状态回复（N33） |

- 是否初始化成功统一叫 `is_initialized()`（不再有 `initialized()` / `is_init()`）。
- 布尔查询必须返回 `bool`：`Online::is_online()` 原来返回 `Status`（`OK` = 0 = 在线），`if (x.is_online())` 恰好在离线时成立，2.7 起改成 `bool`。
- 例外：`snapshot(...)`（在临界区里取一份一致的副本，名字表达“同一时刻”，保留）；数学值类型（`Quaternion`、`MatrixF32`、`Vector3`）沿用数学名（`norm()`、`trace()`、`conj()`）；`PID::get()`；`Rls` 的 `omega()` / `covariance()` / `error()`（沿用算法文献里的符号名）。
- 全局常量带 `ICBSP_` 前缀（`ICBSP_PI` / `ICBSP_PI_F`，`algorithm/math_constants.hpp`），不定义 `PI` 这类通用宏；枚举一律 `enum class`（`DjiMotorType::M3508`）。

### 2.2 库命名不与开发组织耦合

本库要作为 submodule 接入任意工程，名字里不能带单个开发组织 / 团队名（例如 `cubot`）；库名 **ICBSP**（INVC & CUBOT Board Support Package，两个组织共同署名）本身作为前缀使用：

1. **按功能命名**：文件、类型、函数、宏、CMake 目标、FreeRTOS 任务名、CMake 打印与报错文字，一律描述“它是做什么的”，不写“谁写的”。
2. **功能名不够用时加 `ICBSP` 前缀**：按功能起的名字太通用、可能与宿主工程冲突时，宏用 `ICBSP_XXX`、函数用 `icbsp_xxx()`；宿主提供给库的配置宏、功能开关、实例清单一律带 `ICBSP_`；CMake 目标为 `icbsp`，仓库名为 `ICBSP`。
3. **新全局名字先查重**：在宿主工程的 `Drivers/`（含全部 STM32H7 设备头文件与 HAL Legacy 头）、`Middlewares/`（FreeRTOS）、`Core/` 里 `grep -rw <名字>`，不能与 HAL / CMSIS / FreeRTOS / CubeMX 生成代码同名。
4. 只出现在 git 历史、提交说明里的旧名字不追改。

现有名字对照（2026-10-17 由 `cubot_*` 改名）：

| 用途 | 名字 |
| --- | --- |
| 用户配置文件（宿主 `user/board/`） | `hardware_config.h`，保护宏 `HARDWARE_CONFIG_H`；所有可调宏都在这里（缺宏、范围、依赖检查在库的 `service/system/config_check.hpp`） |
| 取配置 | 库内一律 `#include "service/system/config_check.hpp"`（它包含 `hardware_config.h` 并做检查；和 `status_code.hpp` 一样各层都能包含），不直接包含 `hardware_config.h`；宿主代码可以直接包含 `hardware_config.h`。没有默认值头文件。新增可调宏时在 `config_check.hpp` 里同时加缺宏 `#error` 和范围 `static_assert`，并同步模板 |
| 配置宏 | `ICBSP_` 前缀 + 按功能分组：`ICBSP_SYS_TASK_*`、`ICBSP_CAN_TASK_*`、`ICBSP_CAN_*`、`ICBSP_UART_*`（如 `ICBSP_CAN_CMD_EXPIRE_MS`、`ICBSP_UART_ENABLE_FIFO`）；实例清单 `ICBSP_CAN/UART/SPI_INSTANCES` |
| 库入口 | `code/service/system/system.hpp`：`system_init()`、`system_start()` |
| 库任务 | `sys_task`、`can_rx_task`、`can_tx_task`（FreeRTOS 任务名 `sys`、`can_rx`、`can_tx`） |
| CMake 目标 | `icbsp`（OBJECT 库） |

## 3. 注释规范（Doxygen）

> **@file 说明块只写在头文件的最顶部；源文件最顶部不放任何说明，直接以 `#include` 开头。**
> 文件说明、@details、@note、使用示例等全部收敛到头文件顶部；源文件内只保留函数/分区级注释。

```cpp
/**
 * @file bsp_uart.hpp
 * @author 名字
 * @brief 一句话说明这个文件是干什么的
 * @version 0.2
 * @date 日期
 *
 * @todo 待办事项
 *
 * @copyright Copyright (c) 2026
 *
 * @details 详细说明 / 使用示例
 *
 * @note 注意事项
 */
```

- **函数注释**：`@brief`（必须）+ `@param` + `@return` + `@note`；公共接口必须写全，私有函数可只写 `@brief` 或行注释
- **成员变量**：行尾 `///<` 注释
- **分区横幅**：`/* ==================== 分区名 ==================== */`
- **注释语言**：中文；描述"为什么"，而不是复述代码
- 未使用的参数写 `(void)arg;` 并注明

## 4. 类设计模式

1. **板级实例在宿主里**：库里不定义任何板级实例（`bsp_dwt`、`sys_state` 这类库自己的单例除外）。
   外设类（`BspCanT`、`BspUartT`、`BspSpi`、`BspPwm`、`BspGpio`、`BspKey`、`BspEncoder`）的构造是 constexpr，在宿主 `board_cfg.hpp` 里写成 `inline` 全局变量；
   设备类（`DjiMotor`、`DmMotor`、`DeviceBmi088`、`DeviceMotor` …）和 `BspSpiDevice` 的构造不是 constexpr，推荐定义在 `board_cfg.cpp`、头文件里 `extern`。
   设备写成 `inline` 也能用（C++17 起保证只初始化一次），代价是变成动态初始化：每个包含它的 TU 都有一份初始化代码，并注册析构。
2. **实例清单（X-macro），没有登记表**：同类外设实例由宿主 `board_instances.hpp` 的 `ICBSP_CAN/UART/SPI_INSTANCES(X)` 列出，库的 HAL 回调分发、后台任务、
   默认状态树都按清单在编译期展开（`if (h == name.get_handle()) …`）。`init()` 先核对“自己在清单里、且清单里只有自己绑这个句柄”，否则返回 `BAD_ARG`。
   新增一类需要回调分发的外设时照此办理，不要再引入运行时登记表。
3. **模板只有头文件**：模板类（`BspUartT`、`BspCanT`、`DjiMotor`、`DmMotor`、`Rls` …）把实现写在头文件里，任意模板参数都能用；
   回归宿主（DM-MC02 工程）的 `app/compile_probe.cpp` 显式实例化所有头文件模板，让没接这个设备的工程里接口改动也能被编译器检查到；新增头文件模板时在那里加一行。
4. **HAL 中断回调**：放在对应 BSP 的 `.cpp` 里，`extern "C"` 包裹，按清单分发；清单外的同类外设转到弱函数 `icbsp_unhandled_*()`（N30）。
5. **配置结构体 `Config`**：类的构造参数收进类内的 `Config` 结构体，不写一长串裸参数的构造函数；要绑定的总线 / 外设引用单独作参数放在前面（`DmMotor(can, cfg)`、`DeviceBmi088(acc_spi, gyro_spi, cfg)`、`DeviceR9dsT(uart)`），其余进 `Config`。
   例外：`DjiMotor` 仍是裸参数构造（`DjiMotor(can, motor_id, ratio, offset, control_mode, online_timeout_ms)`），是历史接口，待改。
   `Config` 写成**聚合体**：字段带默认成员初始化，不写构造函数；调用处用 C++20 指定初始化器，只写要改的字段：
   ```cpp
   inline ICBSP_DMA_BUFFER(bsp_uart1) BspUartT<uart_mode::dma, 128, 128> bsp_uart1({.huart = &huart1, .mode = UartDir::TxRx, .baudrate = 115200U});
   DmMotor<decltype(bsp_can2)> yaw_motor(bsp_can2, {.model = DmModel::J4340P, .can_id = 0x02, .master_id = 0x12});   // board_cfg.cpp
   ```
   指定初始化器**必须按字段声明顺序写**（可以跳过，不能颠倒）。算法类的 `Config` 字段多、常按位置传（`PID::Config(kp, ki, kd, out_max)`、`Rls::Config(lambda, p0)`），
   可以保留“参数顺序 = 字段顺序”的带默认值构造函数；只传一个参数时别用花括号（`{0.99f}` 也能匹配拷贝构造，有二义性），写成 `X::Config(0.99f)`。
6. **构造函数只做赋值；外设类 constexpr + 平凡析构**：构造函数里只允许成员赋值；任何 FreeRTOS 操作（`xTaskCreate`、`xSemaphoreCreate*`、流缓冲区）、
   `memset` / `snprintf`、清单核对都放进 `init()`，释放放进 `deinit()`。外设类的构造函数写成 `constexpr`、析构函数平凡（不写析构函数）：
   `inline` 全局实例这样才是常量初始化——不进静态构造顺序问题、每个 TU 不各生成一份构造代码，也不注册 `atexit` 析构（N32）。
   宿主测试里用 `constinit` 与 `static_assert(std::is_trivially_destructible_v<T>)` 检查。成员数组要写 `= {}`，否则构造不是常量表达式。
7. **`init()` 可重复调用**：再次 `init()` 先停外设、释放旧资源再重建，失败时回滚；前提是没有任务正在用（例如 `BspSpi` 的 BMI088 刷新任务）。
8. **隐藏逻辑必须显式化**：如 `i_max == 0 → 跟随 out_max`，要写在代码里并注释

## 5. 分层架构

依赖方向（上层可用下层，禁止反向）：

```
宿主 app/（app_init、业务任务）
 └─ 宿主 board/（实例、board_init、实例清单、配置）
     ├─ device/（单设备驱动：motor / sensor / remote / actuator）     tasks/（库任务体）
     │    └──────────────┬──────────────────────────────────────────────┘
     └─ service/（system / comm / monitor / definition）
          └─ bsp/（外设驱动，完全不考虑上层设备）           algorithm/（纯数学，device / service 可用）
```

- 层由目录决定（`code/<层>/…`），规则见 [code/README.md](code/README.md#2-依赖矩阵)，`python3 tools/check_layers.py` 检查
- 唯一的反向依赖：`bsp/`、`tasks/` 经 X-macro 包含宿主的 `board_instances.hpp`
- 跨层通信使用下一层暴露的接口 / 实例；设备层不直接操作 HAL（走 bsp）

## 6. C/C++ 混编

- HAL / FreeRTOS 回调必须 `extern "C"`，防止名称修饰
- C 调 C++ 只通过 `extern "C"` 入口转接（宿主的 `app_init()`、任务入口；库的 `system_*()`）
- 任务函数若被 FreeRTOS 以 C 方式调用，需要 `extern "C"` 且参数为 `void *pvParameters`

## 7. 格式类规则（.clang-format 已固化）

- 2 空格缩进、Allman 大括号（换行）
- `*` `&` 靠右：`uint8_t *data`
- 连续赋值 / 声明对齐；行尾注释对齐
- 不限制行长（`ColumnLimit: 0`）
- 指针自动推导对齐（`DerivePointerAlignment`）

## 8. 断言与初始化失败

`configASSERT` 定义在宿主工程 `Core/Inc/FreeRTOSConfig.h` 的 USER CODE 1 段（内容与 `templates/FreeRTOSConfig_user_code.h` 一致）：

```c
#define configASSERT( x ) do { if ((x) == 0) { fault_on_assert(__FILE__, __LINE__); } } while (0)
```

**有副作用的检查用 `ICBSP_CHECK(expr)`，不要写进 `configASSERT(...)`**（`service/system/fault_record.hpp`）：`configASSERT` 可能被定义成空
（FreeRTOS 默认就是空，发布构建关断言也很常见），写在里面的 `init()` / `xTaskCreate()` 会被整个删掉，系统静默什么都不做。
`ICBSP_CHECK` 总会求值，失败时走同一个 `fault_on_assert()`。纯条件检查（例如 `configASSERT(len > 0)`）照旧用 `configASSERT`。

失败时由 `service/system/fault_record.cpp` 关中断、把种类 / 文件名 / 行号 / tick / IPSR / 任务名写进 `fault_record`（RAM_D1 的 `.noinit` 段，复位后保留），再停机：接着调试器时执行 `BKPT` 停在现场，没接就死循环。栈溢出与内存分配失败钩子（`freertos.c` 的 USER CODE 4 / 5）同样记录后停机。复位后用调试器 `print fault_record` 查看上一次故障。

- **初始化失败用断言**：句柄为空、RTOS 对象创建失败、外设起不来、配置与实物不符，都是“代码 / 配置写错了”，在宿主的 `board_init()` 里**每条 `init()` 单独一行** `ICBSP_CHECK(xxx.init() == Status::OK);`，记录里的行号直接指出是哪一路
- **运行期可恢复的失败返回 `Status`**：总线上的非法帧、超时、缓冲满、外部输入越界交给上层决策，不要断言（一帧噪声不应让整车停机）
- **注册阶段的失败**（`regist()` 等调用 `sys_state.init_error()`）不会当场停机，由初始化末尾的 `system_start()`（内含 `ICBSP_CHECK(sys_state.complete_init() == Status::OK)`）统一停机
- 任务入口先调 `sys_state.wait_running()`：等到运行位才放行；等到初始化失败位时任务自行退出，不会永久阻塞
- 中断里尽量不放断言：ISR 里只做最少校验，非法数据丢掉并计数即可
- 宿主链接脚本必须有 `.dma_buffer` / `.noinit` 段（`templates/linker_sections.ld`），缺了 CMake 配置阶段报错；CubeMX 6.18.1 重新生成会保留已有链接脚本内容，只改几行行尾（`git checkout` 还原即可）
- 库里的可调常量一律经 `hardware_config.h` 取（库内经 `config_check.hpp` 包含，范围检查写在 `config_check.hpp`），不要在库源文件里写死数字，也不要再引入默认值头文件

## 9. C++20 规则

库和宿主都按 C++20 编译（库目标 `-Wall -Wextra -Wshadow`，0 warning）。容易踩的几条：

- **`volatile` 不能复合赋值**：`x++`、`x += n` 对 `volatile` 变量在 C++20 里弃用（会警告），写成 `x = x + 1U`。跨任务 / 中断共享的计数器、标志都是 `volatile`，这条最常见。
- **指定初始化器按声明顺序**：`{.huart = …, .mode = …}` 的字段顺序必须和 `Config` 里的声明顺序一致，可以省略、不能颠倒；不能和位置初始化混用。
- **聚合体 `Config`**：给了默认成员初始化的结构体在 C++20 里仍是聚合体，可以用指定初始化器；一旦写了用户构造函数就不再是聚合体（见第 4 节第 5 条）。
- **constexpr 构造 + 平凡析构**：外设类的 `inline` 全局实例要能常量初始化（见第 4 节第 6 条）；成员里有数组时写 `= {}`。
- **`inline` 变量**：头文件里的全局实例写 `inline`（每个 TU 一份弱定义，链接时合并）；放 `.dma_buffer` 的还要按变量名区分段名（见第 10 节）。
- **`enum class`**、`static_assert`、`if constexpr`、`std::is_trivially_destructible_v` 等照常使用；库不依赖异常与 RTTI，不要在库里 `throw` / `dynamic_cast`；
  动态分配只在初始化期用 `new (std::nothrow)` 并检查返回值。

## 10. `.dma_buffer` 段

H7 的 DMA1 / DMA2 访问不到 DTCM，默认的 `.bss` / `.data` 又在 DTCM，所以 DMA 直接读写的对象（`uart_mode::dma` 的 `BspUartT` 实例、开 DMA 的 `BspSpi` 实例、
宿主自己的 DMA 缓冲）必须放进 AXI SRAM 的 `.dma_buffer` 段：

```cpp
#include "bsp/bsp_dma_buffer.hpp"
inline ICBSP_DMA_BUFFER(bsp_uart1) BspUartT<uart_mode::dma, 128, 128> bsp_uart1({.huart = &huart1});
```

- **一律用宏 `ICBSP_DMA_BUFFER(变量名)`**，它展开成 `__attribute__((section(".dma_buffer.<变量名>")))`。不要手写 `section(".dma_buffer")`：
  `inline` 变量是 COMDAT，每个 TU 各有一份弱定义；段名相同时这些副本的数据会全部进同一个输出段（符号去重了、数据没去），段比实例总和大出几份，或被 `--gc-sections` 剔掉真数据。
- 段是**可加载**的（`>RAM_D1 AT> FLASH`），库在 `constructor(101)` 里把初值从 Flash 拷进 RAM，所以放进去的对象可以有初值（句柄、波特率）。
- 库在 `init()` 里核对：DMA 模式的实例不在 DMA 可达的内存里（`icbsp_dma_reachable()`，按 DMA1/2 与 BDMA 分别判断）就返回 `BAD_ARG`。
- 库假定 D-Cache 关闭，DMA 缓冲不做 Cache 维护。
