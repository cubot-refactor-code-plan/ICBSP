# CAN 回填（undo 1.2）实机回归（2026-11-04）

按 `third_party/stm32_bsp/undo.md` 阶段 1.2，把本仓库原来实测过的 CAN 收发与恢复逻辑回填进 fork 的 `BspCanT`，
同时做完评审 I2 / F3 / F6 / F9 和 fork 引入的 N17~N23、N27~N29、N35，再用 10-17 的 CAN 用例（加 3 项新用例）回归。
用例定义见 `can1_can2.md`，本文只记改动、现象与结论。

## 环境

- 板、工具链同 `README.md`；CAN1 H/L ↔ CAN2 H/L，无终端电阻，1 Mbps。
- 宿主分支 `icbsp-migration`，submodule = stm32-framework `626260c` + 本次工作区改动。
- CubeMX：FDCAN1 / FDCAN2 经典 CAN、RX FIFO0 16 帧、TX FIFO 16 帧、`StdFiltersNbr = 1`。
- 全程没有启动 TIM3、没有写 PB1（BMI088 加热电阻）。

## 诊断：TX 队列模式下同 ID 乱序（C06e）

第一轮 Debug：C06e（运行中把 CAN1 切到 TX 队列模式，同 ID 连发 1000 帧）收到的序列丢 8、乱序 4。10-17 的旧实现是 1000 / 1000 且不乱序。

原因：队列模式下硬件按 ID 优先级发；**同 ID 的多个缓冲按缓冲编号发，不按写入顺序**。新实现的中断续发一次填满所有空位，
同一 ID 有好几帧同时在硬件里，编号小的先发就乱了。旧实现一次只搬一帧，硬件里很少同时有两帧同 ID，所以没暴露（并不是保证）。

修正：记下每个硬件 TX 缓冲里的帧 ID；队列模式下，若下一帧的 ID 已经有一帧在硬件里等，先把它留在一帧大小的暂存位，等那一帧发完再写。
不同 ID 之间仍按队列优先级；FIFO 模式不受影响。修正后 C06e 1000 / 1000、不乱序。

## 诊断 2：总线被占满时的队头阻塞（C06c / C06d）

CAN2 用 0x102 连续占满总线时，CAN1 发送节点 0x200 的周期帧（优先级低于 0x102）永远发不出去。旧实现里它们每 1~5 ms 入队一帧，
把 16 帧软件缓冲和 16 个硬件缓冲都占满，最高优先级的探测帧 0x050 连 `send()` 都进不去（10-17：0~1 / 20、队列模式 0~3 / 20）。

修正：发送节点改用 `send_latest()`，同 ID 的上一帧还没发出去就不再入队。这样 0x200 最多占一个硬件缓冲：
- **队列模式（C06d）**：0x050 进得去，硬件按优先级先发它 —— **20 / 20，送达 0.80 ~ 1.24 ms**；
- **FIFO 模式（C06c）**：硬件严格按入队顺序发，排在前面的那一帧 0x200 发不出去，0x050 只能等 —— 0 / 20。这是 FIFO 模式的固有限制，
  C06c 改为只记录（`SKIP`，code 0xF1F0），文档写明：总线上有更高优先级流量、可能被占满时用 Queue 模式。
