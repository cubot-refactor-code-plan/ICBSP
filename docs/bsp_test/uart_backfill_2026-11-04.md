# UART 回填（undo 1.1）实机回归（2026-11-04）

库从 STM32_BSP 换成 stm32-framework 之后，按 `third_party/stm32_bsp/undo.md` 阶段 1.1 把本仓库原来的 UART 收发状态机回填进 fork 的 `BspUartT`，
再用 10-17 的 UART / RS485 用例回归。用例定义与判据见 `uart_u7_u10.md`、`rs485_u2_u3.md`，本文只记这次的改动、现象与结论。

## 环境

- 板、接线、工具链同 `README.md`（U7 ⇄ U10 跳线；485 口 1 ⇄ 口 2；CMSIS-DAP；OpenOCD 0.12.0+dev；EmberProbe 烧录）。
- 宿主分支 `icbsp-migration`，submodule = stm32-framework `bf8df28` + 本次工作区改动（`code/bsp/bsp_uart.{hpp,cpp}` 等）。
- HAL 时基 TIM8 优先级仍为 4（改回 15 要等 undo 1.4 的 A3，见下文“未做”）。
- 测试固件开关（`app/app_test.hpp`）：UART、RS485 两组；CAN、SPI / BMI088 两组的测试代码还是旧库接口，暂时关闭（1.2 及以后适配）。
  全程没有启动 TIM3、没有写 PB1（BMI088 加热电阻）。

## 库改动（`BspUartT`，保留 fork 的接口，内部换回本仓库实测过的实现）

| 项 | 内容 |
| --- | --- |
| 只有头文件（I1） | 模板成员全部在 `bsp_uart.hpp`，`bsp_uart.cpp` 只剩 HAL 回调分发；任意 `<Transport, RX, TX>` 组合都能用（本工程 U10 恢复 256 字节） |
| RX 循环 DMA（undo 原文那一项） | `init()` 把 `hdmarx` 改成 Circular + 直接模式；IDLE / HT / TC 回调只读 DMA 剩余计数，把“上次读到 → 当前位置”投进流缓冲区（处理回绕）。接收路径不再调用阻塞版 `HAL_DMA_Abort()`，也没有重新挂接收的空窗 |
| N1 | `_tx_write_lock`：发送流缓冲区只有一个写者；启动失败的那一段留在 `_tx_buffer` 里下次先发，中断侧从不写流缓冲区 |
| N2 | `UART_ENABLE_FIFO` 恢复作用（`init()` 打开 UART 硬件 FIFO） |
| N3 | 接收流缓冲区 = 2 × RX_SIZE |
| N4 | 循环 DMA 下不再需要“IDLE 后按剩余计数重算”（位置本来就按剩余计数取） |
| N5 / N6 | 卡死判定看“剩余计数在变或串口仍在移位”；先中止再按剩余计数结算（IT 模式先关发送中断再读 `TxXferCount`） |
| N7 | DMA 句柄修复 `repair_dma_handle()` 计入 `dma_repair_cnt`；`rx_recover()` / 重新 `init()` 期间屏蔽本串口及其 RX / TX DMA 流的 NVIC 中断；中止接收后确保 RX 流真的停了 |
| N8 | 运行中重新 `init()`：先停收发、复位句柄再重建 |
| N9 | `ms_to_ticks()`，`portMAX_DELAY` 不再溢出 |
| N10 | DMA 模式检查 `hdmarx` / `hdmatx`、实例是否在 DMA 可达内存 |
| N11 | **不恢复**软件 DE：RS485 只支持 UART 硬件 DE |
| N12 / F2 / N31 | 在途段 `[_tx_chunk_off, +_tx_chunk_len)` + `_tx_chunk_active`，**调用 HAL 之前**置 active（F2）；`tx_recover()` 持 `_tx_lock` 改写在途段（N31） |
| N13（串口部分，提前做） | `init()` 核对实例在 `BSP_UART_INSTANCES` 里、且是清单里唯一绑该句柄的实例，否则 `BAD_ARG` |
| N24 | 恢复 `HAL_UART_MODULE_ENABLED` 保护 |
| 诊断 | `RxDiag` / `TxDiag` 在 fork 字段之外补回 `dma_repair_cnt` |

## 测试代码改动（宿主 `app/test/`）

- 端口抽象改用 `BspUartT<uart_mode::dma, N, N>`、`get_rx_diag()` / `get_tx_diag()` / `get_rx_health()`、`sys_state.wait_running()`；U13 的额外实例改成清单外实例（`.dma_buffer.<变量名>`）。
- C++20 下 volatile 的 `++` / `--` 改写；CAN 组、物理插拔组在开关为 0 时不编译。
- RS485 组运行时不启动 `app_main.cpp` 的 RS485 应答任务（两者都读 U2 / U3）。
- R03 新增诊断：每次往返超时记一行状态与寄存器快照（`r03_to_log`）、每轮驱动计数增量（`r03_diag`）；`BSP_TEST_R03_ROUNDS` 可重复跑。
- **修正测试时钟 `us_now()` 的回绕错误**（见下节），这是本次唯一的“失败”来源。
- 两个实验开关（默认 0）：`BSP_TEST_RS485_RX_PULLUP`（给 PD6 / PD9 开内部上拉）、`BSP_TEST_RS485_DE_TIME`（改写 DEAT / DEDT）。

## 诊断：R03 / R03b 偶发超时 → 测试时钟回绕

第一轮 Debug 回归 36/37，只有 R03b 1000 次往返里超时 1 次（无 CRC 错、无恢复计数）。10-17 的记录里 -O2 下 R03 也有过 1/1000 的超时“未定位”。

| 实验（各 10 轮 × 1000 次往返） | 失败轮数 | 现象 |
| --- | --- | --- |
| 新库 | 6 | 每次 3 连超时，伴随 1 次 NE / FE、1 次接收重建、几十个垃圾字节；超时瞬间一侧 `gState = BUSY_TX`、`TXE = 0`、`TC = 0` |
| 新库，关 UART FIFO | 6 | 同上 |
| **旧库 STM32_BSP @ cdb34d8** | 6 | 同上（寄存器快照一致） |
| 新库，RX 引脚加内部上拉 | 6 | 垃圾字节与 NE / FE 基本消失，超时仍在 |
| 新库，上拉 + DEAT / DEDT = 16 | 4 | 同上；其中一轮的平均 / 最大往返时间出现 4 291 858 µs / 4 287 162 981 µs |

最后一行的离谱数值暴露了根因：`us_now() = DWT->CYCCNT / 550`，CYCCNT 是 32 位周期计数，550 MHz 下 **约 7.8 s 回绕一次**，
换算出的微秒数在 7 809 031 处跳回 0，而不是在 2³² 处回绕。`us_now() - t0` 跨过这一点变成约 4.29 × 10⁹，
R03 的“最多等 20 ms”立即结束 → 记一次假超时 → 测试马上发下一个请求，和对端还在线上的应答冲突 → CRC 错、垃圾字节、NE / FE、接收重建，于是“3 连超时”。
所谓“发送器停住”的寄存器快照，其实是在发出请求后几微秒内拍的，就是一次正常进行中的发送。每轮 R03 约 4.5 s，约六成的轮次会跨过一次回绕，与 6 / 10 吻合。

修正：`us_now()` 把 CYCCNT 扩展成 64 位再换算（临界区内检测回绕），由每 1 ms 运行一次的错误监视任务保证不漏回绕。
修正后同样 10 轮 × 1000 次：**20 / 20 通过，0 次超时**，往返 4.47 ~ 4.84 ms。RS485 硬件与驱动都没有问题；10-17 记录里 -O2 下那次未定位的超时也是这个原因。

## 观察到但没有处理的

- Debug 下 U04 的 4 Mbps 吞吐（182 / 191 KB/s）比 -O2（203 KB/s）低，是 -O0 的开销；-O2 与 10-17 一致。
- R05 最高档吞吐在不同轮次间波动（53 ~ 91 KB/s），各档无损；受测试接收任务调度影响，判据只看无损。
