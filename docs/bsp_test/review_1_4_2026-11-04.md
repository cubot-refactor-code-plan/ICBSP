# 评审遗留问题（undo 1.4）改动与实机回归（2026-11-04）

按 `third_party/stm32_bsp/undo.md` 阶段 1.4 修评审（`stm32_bsp_review.md`）里 fork 同样存在的问题，HAL 时基 TIM8 优先级从 4 改回 CubeMX 默认的 15，
服务层测试组加 Y06 ~ Y12，再在 Debug 与 -O2 上全组回归。

## 环境

- 板、接线、工具链同 `README.md`；宿主分支 `icbsp-migration`，submodule = stm32-framework 1.3 提交 + 本次工作区改动。
- 全程没有启动 TIM3、没有写 PB1（BMI088 加热电阻），H00 / H99 与监视任务核对全部为 0。
- CubeMX 改动（用户确认后用 CLI 重新生成）：`NVIC.TIM8_UP_TIM13_IRQn` 优先级 4 → 15，生成结果只有 `stm32h7xx_hal_conf.h` 的 `TICK_INT_PRIORITY` 变了。

## 结果

### Debug，TIM8 = 4，不浸泡（最后故意触发 BusFault）

87 项：**83 通过、3 跳过、1 失败**（原始表 `raw/2026-11-04_review14_all_debug_tim8_4.txt`）。

- 跳过：Y12（第一次运行，没有上一次的记录）、C06c（FIFO 模式只记录）、P05（不浸泡时不跑）。
- 服务层 Y01 ~ Y11 全部通过；UART / RS485 / CAN / SPI 其余用例全部通过。
- **故意的 BusFault（A5）**：`fault_record` = HARD_FAULT、HFSR.FORCED、CFSR = 0x8200（PRECISERR + BFARVALID）、BFAR = 0xA000_0000、任务 `bsp_test`、
  EXC_RETURN = 0xFFFFFFED（PSP）、**PC = 0x0803_0292，落在 `bsp_test_fault_now()`（0x0803_0284）里**——出错位置从任务栈正确解出。
- **P02 失败：5 帧不合理**（|acc| 超出 7 ~ 12 m/s²），SPI 层 0 错误、ID 核对 0 错、update 次数 = 中断数。5 帧全在约 2 s 内，
  Z 轴读数是连续的 10.9 → 12.6 m/s²，角速度很小、前后帧平滑：是板子受到的真实加速度，不是读错。

### Debug，TIM8 = 15，5 分钟浸泡

90 项：**86 通过、2 跳过、2 失败**（原始表 `raw/2026-11-04_review14_all_debug_tim8_15_soak5.txt`）。

- **TIM8 改回 15 后正常启动**（BMI088 与串口在调度器启动前的初始化不再依赖 HAL tick，A3），全程没有卡死。
- U14（UART 双向 5 min）300000 / 300000、R06（RS485 5 min）265 轮无损、C09（CAN 双向 5 min）300000 / 300000，P05（SPI 争用 5 min）0 错、0 不合理帧。
- **Y12 读到了上一轮故意触发的那次故障**（HARD_FAULT、CFSR 0x8200、BFAR 0xA000_0000、PC 0x0803_0292、count 1）：复位（不是上电）后记录保留，A8 的上电清零没有误清。
- Y09：sys / can_rx / imu 的优先级 52 / 54 / 53（configMAX_PRIORITIES = 56，osPriorityNormal = 24）。
- Y08：两个任务连续读 10 s，0 次倒退、0 次跳变，DWT 时间与 tick 差 307 µs。
- **P01 2 帧、P02 27 帧不合理**，SPI 层同样 0 错误、ID 0 错、update = 中断数。异常日志里一串帧在约 40 ms 内 Z 轴 3 → 17 → 30 → 3 m/s² 来回振荡、
  角速度不大——是敲击 / 桌面振动一类的机械冲击（衰减振荡），读错或混帧给不出 30 m/s²。1.3 的两轮（白天）都是 0；与 10-28 记录里“碰板”的结论一致。
  判据（静止）在这两轮不成立，不算库的问题；需要时在板子不受扰动的时段重跑 P01 / P02。

### -O2，TIM8 = 15，5 分钟浸泡（2026-11-05 补跑）

90 项：**86 通过、2 跳过、2 失败**（原始表 `raw/2026-11-05_review14_all_O2_tim8_15_soak5.txt`）。第一次烧录确认超时（EmberProbe 的 24 小时授权一次只记一个 ELF 路径），用户要求后重新授权补跑。

- **TIM8 = 15 在 -O2 下正常启动、全程没有卡死**（原来的卡死只在 -O2 出现）：U14 300000 / 300000、R06 266 轮无损、C09 300000 / 300000、C06d 20 / 20、P05 0 错 0 不合理帧。
  TIM8 改回 15 至此 Debug 与 -O2 都验证过。
- 服务层 Y01 ~ Y11 全部通过（Y08：DWT 与 tick 差 415 µs；Y09：52 / 54 / 53）。
- **P01 105 帧、P02 6 帧不合理**，SPI 层仍然 0 错误、ID 0 错、update = 中断数。异常日志：分成 7 簇（第 1329、1416、1444、1487、1643、1647、1695 s），
  每簇里 |acc| 在几毫秒内 6 ↔ 15 m/s² 来回摆，前后帧连续——和前两轮一样是机械振动。顺带核对了板上的振源：蜂鸣器 TIM12 的 CCR2 = 0（静音；ARR 停在开机那声 3 kHz），
  加热电阻 TIM3 的 CEN / CC4E / CCR4 全 0。三轮（11-04 晚到 11-05）都出现、1.3 的两轮（11-04 白天）都没有；判据要求板子静止，这几轮不满足，没有证据指向库。
  要彻底排除，可以在确认没人碰桌子的时段单跑 SPI 组（约 25 min），或者用 1.3 的固件同一时段对照。
- **Y12 读到一条新的故障记录**（count 1 → 2）：HARD_FAULT（FORCED）、CFSR 0x8600（PRECISERR + IMPRECISERR + BFARVALID）、**BFAR = 0x04C1_1DB7**、EXC_RETURN 0xFFFFFFF9（线程模式、MSP）、
  tick 0、任务名为空、PC 没解码。0x04C11DB7 是 CRC-32 多项式。推断：EmberProbe 烧录前先用 OpenOCD 的 `verify_image_checksum` 在目标 CPU 上跑 CRC 算法（日志里的 “checksum mismatch”），
  算法出错时 CPU 按 Flash 里**旧固件**的向量表进了它的 `fault_on_exception()`；OpenOCD 的工作区覆盖了 RAM，调度器状态读成“没启动”，所以 tick / 任务名为空。
  两个测试固件的 `fault_record` 恰好都在 0x2400_2F20，-O2 固件的 Y12 就读到了旧固件写的这条。上一次烧录没出现，是因为那时旧固件正停在故意的 BusFault 里（重入不再记录）。
  这条是**烧录过程**留下的，不是固件的问题；要确认得在目标上再跑一次 OpenOCD 的校验算法（会改 RAM、执行代码），没有做。影响：每次烧录后 `fault_record` 可能多一条假记录，
  看记录时以 `boot_rsr` / tick 区分。
